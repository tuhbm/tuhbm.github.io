블로그 대표 이미지를 SVG로 만들고 resvg로 PNG 변환하기 (한글 폰트와 삽질 기록)

왜 SVG로 만들었나

글마다 대표 이미지를 붙이고 싶었다. 디자인 툴을 열어서 하나씩 만들면 하루에 여러 편 올리는 속도를 못 따라간다. 그래서 틀을 코드로 만들고 숫자와 문구만 바꿔 끼우는 방식으로 갔다. SVG는 텍스트 파일이라 코드로 찍어내기 좋고, 마지막에 PNG로만 바꾸면 어디서든 열린다.

흐름은 단순하다. 문구를 담은 JSON을 읽어서 SVG를 만들고, 그걸 PNG로 변환해 source/images에 둔다.

변환은 resvg

브라우저 없이 Node에서 SVG를 PNG로 바꿔 주는 라이브러리를 찾다가 @resvg/resvg-js를 골랐다. 헤드리스 브라우저를 띄우는 것보다 가볍고 빠르다. 변환 코드는 이게 전부다.

옵션 세 개만 짚는다.

  • fitTo: 결과 너비를 1536px로 맞춘다. SVG의 viewBox 비율은 그대로 유지된다.
  • font.loadSystemFonts: 시스템에 설치된 폰트를 불러온다. 한글이 나오게 하려면 사실상 필수다.
  • background: 투명 배경 대신 흰 배경으로 깔아 준다.

한글이 네모로 나왔다

한글을 그냥 쓰면 글자가 □로 나오거나 빠질 수 있다. 원인은 단순하다. resvg는 브라우저가 아니라서 웹폰트나 CSS 폴백을 알아서 해 주지 않는다. loadSystemFonts: true를 켜고, SVG의 텍스트에 폰트 이름을 직접 적어 줘야 한다.

Windows에서는 Malgun Gothic(맑은 고딕)이 기본으로 있어서 이게 잘 통했다. 다른 OS에서 돌릴 때는 거기 설치된 한글 폰트 이름으로 바꿔야 한다. 한글은 글자 폭도 넓어서, 알약 모양 배경(rect)을 영문 기준으로 잡았다가 글자가 삐져나오는 일이 잦았다. text-anchor="middle"로 가운데 정렬하고 배경은 넉넉히 잡는 게 마음 편하다.

요소가 통째로 사라지는 함정들

변환은 에러 없이 끝났는데 이미지에서 뭔가 빠져 있는 경우가 제일 힘들었다. 겪은 것만 적는다.

1. 속성값 끝의 공백. width="180 "처럼 끝에 공백이 하나 들어가면 그 요소가 통째로 안 그려졌다. 템플릿 문자열로 숫자를 이어 붙이다가 생겼다. 에러가 안 나서 찾는 데 오래 걸렸다.

2. & 문자. 문구에 R&D를 넣었더니 SVG 자체가 파싱에 실패했다. XML이라서 &는 &amp;로 써야 한다.

3. id 충돌. 이게 제일 헷갈렸다. 그라데이션과 그림자 필터가 같은 id를 쓰면 한쪽이 무시돼서 도형이 안 보이거나 검게 나왔다. 공통 필터를 정의해 두는 함수가 있었는데, 거기서 쓰는 id와 내가 새로 만든 그라데이션 id가 겹친 것이었다. 접두어 규칙을 정해서 겹치지 않게 했다.

4. 겹쳐 그리는 순서. SVG는 나중에 그린 게 위에 올라온다. 텍스트가 도형 뒤에 가려져서 안 보이면 코드 순서를 바꾸면 된다.

결과를 꼭 눈으로 본다

자동화를 해 놓으면 결과를 안 보고 넘기고 싶어지는데, 그림은 코드가 맞아도 글자가 넘치거나 카드에 가려지는 일이 생긴다. 나는 변환 직후 PNG를 직접 열어서 텍스트가 카드 밖으로 나가지 않는지, 요소가 서로 겹치지 않는지 확인한다. 문구 길이는 칩이나 카드 폭에 맞춰 짧게 줄이는 쪽으로 정리했다.

정리

  • @resvg/resvg-js로 Node만으로 SVG → PNG 변환이 된다.
  • 한글은 loadSystemFonts: true와 font-family 지정이 둘 다 필요하다.
  • 에러 없이 요소가 사라지면 속성값 공백, &, id 충돌부터 의심한다.
  • 만든 이미지는 반드시 눈으로 확인한다.

글마다 다른 이미지를 붙이는 일이 이제는 JSON 한 줄 고치는 일로 바뀌어서, 매일 글을 올리는 부담이 많이 줄었다.

마크다운 볼드(**)가 그대로 노출될 때, 원인은 한글 조사였다

별표가 화면에 그대로 보인다

블로그 글을 올리고 나서 확인하는데 이상한 데가 있었다. 분명 굵게 쓴 부분인데 화면에는 이렇게 나왔다.

볼드가 적용되지 않고 별표 네 개가 글자 그대로 남아 있었다. 같은 글의 다른 볼드는 멀쩡해서 더 헷갈렸다. 비교해 보니 깨진 곳에는 공통점이 있었다.

  • 닫는 ** 바로 앞이 %, 따옴표, 괄호 같은 문장부호이고
  • 바로 뒤에 로, 를, 이 같은 한글 조사가 붙어 있었다

왜 그런가

Hexo의 마크다운 렌더러(marked)는 CommonMark 규칙을 따른다. 강조(**)를 닫으려면 닫는 구분자가 “오른쪽에 붙은(right-flanking)” 조건을 만족해야 한다. 규칙을 줄이면 이렇다.

  • 닫는 **의 바로 앞이 공백이면 안 된다.
  • 닫는 **의 바로 앞이 문장부호라면, 바로 뒤는 공백이거나 문장부호여야 한다.

**9%**로를 보면 ** 앞이 %(문장부호)인데 뒤가 로(글자)라서 이 조건에 걸린다. 그래서 **를 닫는 기호로 인정하지 않고 일반 문자로 두는 것이다. 영어는 **9%** is처럼 뒤에 공백이 오는 경우가 많아 잘 안 보이지만, 한글은 조사가 바로 붙으니 자주 걸린다.

이렇게 쓰면 깨진다

깨지는 예 이유
**9%**로 확정 앞이 %, 뒤가 한글
**"신중"**이라고 앞이 따옴표, 뒤가 한글
**(예정)**이다 앞이 괄호, 뒤가 한글

고치는 방법

1. 볼드 경계를 글자나 숫자로 끝낸다. 문장부호를 볼드 안쪽 끝에 두지 말고, 한글이나 숫자로 끝나게 문구를 바꾼다.

2. 따옴표는 볼드 밖에 둔다. **"신중"**이라고 대신 "**신중**"이라고로 쓰면 된다.

3. 그래도 필요하면 HTML을 쓴다. <strong>9%</strong>로는 이 규칙과 상관없이 동작한다. 다만 마크다운 파일이 지저분해져서 나는 잘 쓰지 않는다.

확인 습관

눈으로 하나하나 찾기는 어려우니 빌드한 HTML에서 별표가 남아 있는지 검색한다.

결과가 비어 있으면 깨진 볼드가 없는 것이다. 나는 하루 글을 올릴 때마다 이 한 줄을 돌린다. 한 번 나오면 해당 글을 열어서 ** 주변만 고치면 되니 금방이다.

마크다운은 “일단 되겠지” 하고 쓰기 쉬운데, 한글은 조사 때문에 영어권 예제가 그대로 안 통하는 경우가 있다는 걸 이번에 제대로 배웠다.

Hexo 머리말(front-matter) YAML 때문에 글 한 편이 사라진 날

10편을 썼는데 9편만 나왔다

하루에 글 10편을 올리는 날이었다. 로컬에서 빌드하고 나서 습관처럼 오늘 날짜 폴더의 글 수를 셌는데 9개였다. 에러 메시지는 분명 떴는데 빌드는 끝까지 돌아서, 그냥 지나치면 한 편이 빠진 채로 푸시할 뻔했다.

로그를 올려 보니 이랬다.

Hexo는 글 하나의 머리말이 YAML로 읽히지 않아도 프로세스를 멈추지 않고 그 글만 건너뛴다. 그래서 빌드 성공처럼 보이는 게 함정이다.

범인은 작은따옴표 한 글자

문제의 글은 이런 머리말을 갖고 있었다.

YAML에서 값이 '나 "로 시작하면 문자열 전체가 따옴표로 감싸진 값이라고 해석한다. 그런데 '국민 아버지' 뒤에 글자(로 불린...)가 더 붙어 있으니 문법이 깨진다. 제목 말머리에 인용부호를 쓰고 싶어서 습관처럼 쓴 게 화근이었다.

고치는 방법은 둘이다. 따옴표로 시작하지 않게 문장을 바꾸거나, 아예 값 전체를 따옴표로 감싸고 안쪽 따옴표를 이스케이프하는 것이다. 나는 앞의 방법을 골랐다.

같은 계열로 터지는 것들

겪어 보니 머리말 값에서 조심해야 할 건 대략 이렇다.

상황 결과
값이 ' 또는 "로 시작 따옴표 짝이 안 맞으면 파싱 실패
값 중간에 : (콜론+공백) 새 키로 해석돼 구조가 깨짐
값이 #로 시작하거나 중간에 # 뒤쪽이 주석으로 잘림
값이 *, &, !, %, @로 시작 YAML 특수 문자로 해석
탭 문자 들여쓰기 YAML은 탭 들여쓰기를 허용하지 않음

제목에 : 가 필요하면 —(줄표)나 -로 바꾸는 게 제일 간단했다. 이 블로그는 글이 많아서 아예 규칙으로 정해 뒀다. 제목과 설명은 따옴표로 시작하지 않고, 값 중간에 콜론+공백을 쓰지 않는다.

재발 방지: 푸시 전 두 가지 확인

1. 글 수를 센다. 하루에 올리는 글 수가 정해져 있으니 빌드 뒤에 개수만 비교해도 빠진 글을 바로 알 수 있다.

2. YAML을 직접 파싱해 본다. Hexo가 쓰는 js-yaml을 그대로 써서 머리말만 검사하는 스크립트다. 에러가 난 글 이름을 바로 알려 준다.

글이 수백 편이어도 몇 초면 끝난다. 이걸 푸시 전에 한 번 돌리는 습관을 들였다.

마무리

에러가 났는데도 빌드가 “성공”하는 도구는 로그를 안 보면 놓친다. 사람이 눈으로 확인하는 대신 글 수와 YAML 검사 같은 기계적인 체크를 걸어 두는 게 마음이 편하다. 내 경우에는 글을 빨리 많이 쓰다 보니 그냥 지나칠 위험이 높아서 더 그랬다.

sitemap의 lastmod가 배포할 때마다 바뀌는 이유 (Hexo)

증상

어느 날 사이트맵을 열어 보니 이상했다. 새로 쓴 글이 아닌데도 모든 URL의 <lastmod>가 마지막 배포 날짜로 찍혀 있었다. 글은 하나도 안 고쳤는데 배포할 때마다 전부 “방금 수정됨”이 되는 것이다.

lastmod는 검색엔진에 “이 페이지 내용이 언제 바뀌었는지” 알려 주는 값이다. 전부 오늘 날짜로 나오면 검색엔진 입장에서는 믿을 수 없는 값이 되고, 크롤링 우선순위에도 도움이 안 된다. 새로 생기거나 실제로 고친 글만 날짜가 바뀌어야 맞다.

범위부터 좁혔다

사이트맵은 hexo-generator-sitemap이 만든다. 이 플러그인은 글의 updated 값을 lastmod로 쓴다. 그럼 updated는 어디서 올까.

Hexo는 글 머리말에 updated가 없으면 기본적으로 파일의 수정 시각(mtime)을 쓴다. 문제는 여기였다. 내 배포는 GitHub Actions가 매번 저장소를 새로 체크아웃해서 빌드한다. 체크아웃하는 순간 모든 파일의 mtime이 “지금”이 된다. 그러니 빌드할 때마다 모든 글의 updated가 빌드 시각이 되고, 사이트맵의 lastmod도 전부 배포 시각이 되는 것이었다.

로컬에서는 파일을 안 건드리면 mtime이 그대로라, 이 문제는 CI에서 매번 새로 체크아웃하는 구조에서만 드러난다.

해결은 설정 한 줄

_config.yml에 이 옵션이 있었다.

updated가 비어 있을 때 무엇을 쓸지 정하는 옵션이다. 기본값은 mtime이고 date(작성일), empty(안 씀)도 고를 수 있다. date로 바꾸면 updated가 없는 글은 작성일을 쓴다. 이제 배포를 몇 번 해도 lastmod는 글을 쓴 날 그대로다. 내용을 정말 고친 글에만 머리말에 updated:를 직접 적어 주면 그 날짜로 바뀐다.

홈과 카테고리 페이지는 따로 손봤다

글 URL은 이걸로 해결됐는데 홈, 태그, 카테고리 URL의 lastmod는 여전히 배포 시각이었다. 플러그인의 기본 템플릿이 이쪽에는 “현재 시각”을 넣고 있어서다. 그래서 템플릿을 직접 만들어 연결했다.

템플릿에서 홈은 가장 최근 글의 날짜로, 태그는 소속 글 중 가장 최근 날짜로 고정했다.

이러면 새 글을 쓰기 전까지는 홈의 날짜도 변하지 않는다.

같이 정리한 것들

이 과정에서 사이트맵 쪽 문제를 몇 개 더 정리했다.

  • 사이트맵 플러그인이 중복으로 설치돼 있어서 하나를 지웠다.
  • 색인형(sitemap index) 구조를 평면 단일 파일로 바꿨다. 굳이 쪼갤 필요가 없다고 판단했다.
  • 서치콘솔이 예전에 sitemap.xml을 읽은 판정을 캐시해 두고 새로 안 읽는 것 같아서, 내용이 같은 sitemap.txt를 함께 만들었다. 한 번도 본 적 없는 새 URL이라 처음부터 새로 읽게 하려는 용도다.
  • robots.txt에 사이트맵 주소를 등록했다.

확인하는 방법

배포하고 나서 sitemap.xml을 열어 몇 개만 보면 된다. 오래된 글의 lastmod가 작성일 그대로인지, 최근에 쓴 글만 최근 날짜인지 확인하면 된다. 배포를 한 번 더 해도 값이 안 바뀌면 성공이다.

정리하면, CI에서 매번 새로 체크아웃하는 구조에서는 파일 mtime을 믿으면 안 된다. 날짜가 의미를 가지는 값은 파일 시스템이 아니라 글 머리말에 직접 두는 게 안전하다.

Hexo 블로그에 예약 발행 붙이기 (future 옵션 + GitHub Actions cron)

시작은 휴가였다

블로그에 글을 매일 올리다 보니 며칠 자리를 비울 때가 문제였다. 워드프레스나 티스토리에는 예약 발행이 기본으로 있는데 Hexo는 정적 사이트 생성기라 그런 게 없다. 글을 미리 써 두고 “내일 아침 9시에 열려라” 하는 걸 어떻게 만들지 고민하다가, 의외로 설정 한 줄과 워크플로 몇 줄로 끝나서 정리해 둔다.

원리부터

Hexo는 hexo generate 할 때 글의 date가 현재 시각보다 미래면 기본적으로 건너뛴다. _config.yml에 이런 옵션이 있다.

Hexo의 기본값은 true라서 미래 날짜 글도 그냥 빌드된다. 나는 일부러 false를 명시해 뒀다. 이러면 글 머리말에 date: 2026-10-30 13:30:00을 적어 두고 푸시해도, 13시 30분 전에 빌드된 결과물에는 그 글이 없다.

여기까지는 “숨기기”일 뿐이다. 시간이 지나서 다시 빌드를 돌려줘야 글이 나타난다. 그래서 필요한 게 정해진 시각마다 빌드를 돌려주는 스케줄러였고, 이미 GitHub Actions로 배포하고 있어서 schedule 트리거를 추가했다.

워크플로

내 구조는 이렇다. 소스는 gh-pages 브랜치에 있고, Actions가 빌드해서 master에 올린다. 거기에 cron만 붙이면 된다.

cron 표현에서 주의할 점이 몇 가지 있었다.

  • UTC 기준이다. 0-5시는 한국 시간으로 09~14시다. 아침 9시부터 오후 2시까지 30분 간격으로 돈다.
  • 분을 0,30이 아니라 17, 47로 잡았다. 정각 언저리에는 전 세계 예약 실행이 몰려서 늦게 돌거나 가끔 빠진다는 얘기를 봐서 일부러 피했다. 실제로 17분, 47분으로 바꾼 뒤로는 큰 문제가 없었다.
  • 그래도 GitHub 부하에 따라 몇 분에서 수십 분 늦을 수 있다. 정확히 13시 30분 땡에 열리는 건 아니고, 13시 30분 이후 첫 번째 빌드에서 열린다고 생각하면 마음이 편하다.
  • workflow_dispatch를 같이 넣어 두면 급할 때 Actions 탭에서 수동으로 돌릴 수 있다.

푸시 빌드와 예약 빌드가 겹치면 master 푸시가 충돌할 수 있어서 동시 실행 그룹도 걸어 뒀다.

cancel-in-progress: false가 포인트다. 이미 돌고 있는 빌드를 죽이지 않고 뒤에 오는 걸 기다리게 한다.

삽질 두 개

1. 타임존

한국 시간 기준으로 돌리려면 보통 _config.yml에 timezone: Asia/Seoul을 넣는다. 그런데 Actions 러너는 UTC라서, 이 설정을 켜면 새벽 0시부터 9시 사이에 올린 글 9편의 퍼머링크 날짜가 하루 앞당겨진다. 글 주소에 날짜가 들어가는 구조라서 기존 URL이 깨지는 일이다. 그래서 이 방법은 쓰지 않았다.

결국 설정 대신 빌드 단계에서 환경변수로 풀었다.

TZ=Asia/Seoul이면 날짜 해석도 퍼머링크도 모두 한국 시간이라 로컬(Windows) 빌드 결과와 똑같다. 기존 URL도 그대로다.

2. npm ci가 실패한다

러너에서 npm ci가 Missing: chokidar@3.6.0 from lock file 같은 메시지를 뱉으며 죽었다. 원인은 내 로컬 npm(11)이 만든 package-lock.json을 Node 20에 딸린 npm 10이 읽지 못해서였다. 워크플로의 Node를 24로 올렸더니 해결됐다. lock 파일을 만든 npm 메이저 버전과 CI의 npm 버전을 맞춰야 한다는 교훈.

로컬에서 예약 글까지 확인하기

future: false의 부작용은 로컬에서 hexo generate를 돌려도 예약 글이 안 보인다는 것이다. 맞게 쓴 건지 확인이 안 되니 불안했다. 그래서 설정을 코드로 덮어쓰는 작은 스크립트를 만들었다.

hexo clean 하고 node tools/preview-future.js를 돌리면 예약 글까지 public/에 만들어진다. 글 수나 깨진 곳을 이걸로 확인한 뒤에 푸시한다.

쓰다 보니 알게 된 것들

  • 예약 시각이 지났는데 안 열렸다면 대개 아직 다음 cron이 안 돈 것이다. 급하면 workflow_dispatch로 수동 실행하면 된다.
  • 반대로 “지금 당장 열어야지” 싶으면 글의 date를 현재보다 과거로 바꿔서 푸시하면 된다. 푸시 트리거가 바로 빌드를 돌린다.
  • 배포 직후에는 CDN이 반영되는 데 1~2분 걸려 404가 한두 번 뜰 수 있다. 놀라지 말고 한 번 더 확인하면 된다.

설정은 간단한데 시간대와 npm 버전에서 시간을 꽤 썼다. 비슷하게 Actions로 정적 사이트를 배포하는 분이라면 이 두 가지는 미리 체크해 보면 좋겠다.
